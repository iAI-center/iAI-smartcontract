SmartChefV4 - Final Implementation Approach

DOCUMENT VERSION: Approach-02 (Final Implementation)
DATE: June 15, 2025
CONTRACT: SmartChefInitializableV4.sol

===============================================================================
OVERVIEW
===============================================================================

SmartChefV4 implements a DeFi yield farming protocol with a mandatory locking 
mechanism. This approach document outlines the final implementation strategy 
that addresses all requirements while ensuring gas efficiency and code clarity.

===============================================================================
CORE ARCHITECTURE
===============================================================================

1. USER INFO STRUCTURE (Optimized)
   - amount: uint256           // Staked token amount
   - rewardDebt: uint256       // Reward debt for current pending rewards
   - heldRewards: uint256      // Rewards accumulated during lock periods
   - lockEndBlock: uint256     // Block when lock period ends

   REMOVED FIELDS:
   - lastActionBlock: Eliminated as redundant (only lockEndBlock needed)

2. GLOBAL STATE VARIABLES
   - lockingPeriod: uint256    // Lock duration in blocks
   - accTokenPerShare: uint256 // Accumulated rewards per share
   - totalStakedSupply: uint256// Total tokens staked across all users

===============================================================================
LOCKING MECHANISM IMPLEMENTATION
===============================================================================

1. LOCK PERIOD CALCULATION
   - Uses block-based timing (more reliable than timestamps)
   - lockEndBlock = currentBlock + lockingPeriod
   - Reset on every deposit action only

2. LOCK PERIOD ENFORCEMENT
   - withdraw(): Requires block.number >= user.lockEndBlock
   - claimRewards(): Requires block.number >= user.lockEndBlock
   - emergencyWithdraw(): Bypasses lock (emergency only)

3. LOCK PERIOD UPDATES
   - Only allowed before pool starts (block.number < startBlock)
   - Enforced by updateLockingPeriod() function

===============================================================================
REWARD SYSTEM ARCHITECTURE
===============================================================================

1. DUAL REWARD TRACKING
   
   A. HELD REWARDS (user.heldRewards)
      - Accumulated during lock periods
      - Not claimable until lock expires
      - Persistent across deposits
   
   B. PENDING REWARDS (calculated dynamically)
      - Earned after lock period expires
      - Calculated using standard farming formula
      - Immediately claimable after lock expiry

2. REWARD CALCULATION FORMULA
   
   Standard Farming: pending = (amount * accTokenPerShare / PRECISION_FACTOR) - rewardDebt
   
   Total Claimable: heldRewards + pending (only if lock expired)

3. REWARD DISTRIBUTION LOGIC
   
   DURING LOCK PERIOD:
   - New rewards → Add to heldRewards
   - No reward distribution
   
   AFTER LOCK EXPIRY:
   - All rewards (held + pending) → Transfer to user
   - Reset heldRewards to 0

===============================================================================
FUNCTION IMPLEMENTATION DETAILS
===============================================================================

1. DEPOSIT FUNCTION
   
   FLOW:
   a) Validate amount and user limits
   b) Update pool rewards
   c) Handle existing stake rewards:
      - If lock expired: Transfer all rewards (held + pending)
      - If still locked: Add pending to heldRewards
   d) Process new deposit
   e) Reset lock period: lockEndBlock = block.number + lockingPeriod
   f) Update rewardDebt

   KEY FEATURES:
   - Always resets lock period
   - Handles reward claiming automatically
   - Supports zero-amount deposits for reward claiming (when unlocked)

2. WITHDRAW FUNCTION
   
   FLOW:
   a) Validate withdrawal amount
   b) Enforce lock restriction: require(block.number >= user.lockEndBlock)
   c) Update pool rewards
   d) Calculate and transfer all rewards (held + pending)
   e) Process token withdrawal
   f) Update rewardDebt (NO lock period reset)

   KEY FEATURES:
   - Strict lock enforcement
   - Automatic reward claiming on withdrawal
   - Does not reset lock period

3. CLAIM REWARDS FUNCTION
   
   FLOW:
   a) Validate user has stake
   b) Enforce lock restriction: require(block.number >= user.lockEndBlock)
   c) Update pool rewards
   d) Calculate and transfer all rewards (held + pending)
   e) Reset heldRewards to 0
   f) Update rewardDebt

   KEY FEATURES:
   - Allows reward claiming without withdrawal
   - Same lock enforcement as withdraw

4. EMERGENCY WITHDRAW FUNCTION
   
   FLOW:
   a) Calculate total staked amount
   b) Reset all user state to zero
   c) Transfer staked tokens only (NO REWARDS)
   d) Bypass all lock restrictions

   KEY FEATURES:
   - Emergency escape mechanism
   - Forfeits all rewards (held + pending)
   - No lock period restrictions

===============================================================================
ADMINISTRATIVE FUNCTIONS
===============================================================================

1. OWNER-ONLY FUNCTIONS (Pre-Start Only)
   - updateLockingPeriod(): Modify lock duration
   - updateRewardPerBlock(): Adjust reward rate
   - updateStartAndEndBlocks(): Modify pool timing

2. OWNER-ONLY FUNCTIONS (Anytime)
   - stopReward(): Emergency reward halt
   - emergencyRewardWithdraw(): Extract reward tokens
   - recoverWrongTokens(): Recover accidentally sent tokens
   - updatePoolLimitPerUser(): Adjust user limits

3. RESTRICTION ENFORCEMENT
   - All pre-start functions: require(block.number < startBlock)
   - Prevents manipulation after pool activation

===============================================================================
VIEW FUNCTIONS FOR FRONTEND INTEGRATION
===============================================================================

1. REWARD QUERIES
   - pendingReward(user): Current pending rewards
   - totalClaimableRewards(user): Total claimable (held + pending) if unlocked
   - heldRewards(user): Rewards held during lock periods

2. LOCK STATUS QUERIES
   - isInLockPeriod(user): Boolean lock status
   - getLockEndBlock(user): Lock expiry block number

3. POOL STATUS QUERIES
   - isPoolActive(): Pool operational status
   - getUserStakedAmount(user): User's staked amount

===============================================================================
GAS OPTIMIZATION STRATEGIES
===============================================================================

1. STORAGE OPTIMIZATION
   - Removed redundant lastActionBlock field
   - Consolidated reward tracking in minimal fields
   - Efficient struct packing

2. COMPUTATION OPTIMIZATION
   - Single reward calculation per transaction
   - Batch reward processing in deposit/withdraw
   - Avoid unnecessary state updates

3. TRANSFER OPTIMIZATION
   - Combined reward transfers (held + pending)
   - Single token transfer per operation
   - Efficient ERC20 interactions

===============================================================================
SECURITY CONSIDERATIONS
===============================================================================

1. REENTRANCY PROTECTION
   - nonReentrant modifier on all state-changing functions
   - Checks-Effects-Interactions pattern

2. ACCESS CONTROL
   - Ownable pattern for administrative functions
   - Factory-based initialization
   - Strict validation of parameters

3. ARITHMETIC SAFETY
   - SafeMath patterns (Solidity 0.8.27 built-in)
   - Precision factor for decimal calculations
   - Overflow protection

4. LOCK PERIOD INTEGRITY
   - Block-based timing (immune to timestamp manipulation)
   - Strict enforcement in all relevant functions
   - Emergency bypass only in emergencyWithdraw

===============================================================================
ERROR HANDLING AND EDGE CASES
===============================================================================

1. COMMON ERROR SCENARIOS
   - "Cannot withdraw during lock period"
   - "Still in lock period" (for claims)
   - "Amount to withdraw too high"
   - "No staked tokens"
   - "No rewards to claim"

2. EDGE CASE HANDLING
   - Zero amount deposits (allowed for reward claiming when unlocked)
   - Full withdrawals (automatic cleanup)
   - Pool end scenarios (reward calculation stops)
   - Emergency situations (bypass all restrictions)

   - Non-zero addresses
   - Positive lock period
